# Task 1 – Class Design Review

## 1.1 Diagnose the design

The original payroll classes have these design problems:

1. **Repeated fields:** Professor and LabAssistant both repeat name, id and basic salary.
2. **Repeated pay calculation:** The basic salary plus 42% allowance formula appears in more than one class.
3. **Public data:** Public fields can be changed to invalid values from anywhere. Data should be private or protected and accessed through member functions.
4. **Inconsistent names:** `name`/`nm` and `id`/`code` represent the same information but use different names.
5. **Unused field:** `da` is declared but not used in the pay calculation.
6. **Magic number:** `0.42` has no meaningful name or explanation. It should be a named constant such as `DA_RATE`.
7. **Difficult extension:** Adding a new staff type requires another unrelated class and more separate processing code.
8. **No common processing:** The three classes cannot be stored and processed uniformly in a single collection of base-class pointers.

## 1.2 Corrected hierarchy

`Staff` is an abstract base class containing common data and a pure virtual `pay()` function. `Professor`, `LabAssistant` and `GuestFaculty` publicly inherit from it and implement their own pay calculation.

The shared allowance calculation is placed in the base class. GuestFaculty uses hours multiplied by rate.

### UML class diagram

```text
                 <<abstract>>
                    Staff
        -----------------------------
        - name : string
        - id : int
        - basic : double
        -----------------------------
        + pay() : double {abstract}
        + print() : void
                    ^
          __________|__________
         |          |          |
     Professor  LabAssistant GuestFaculty
     ---------  ------------  ------------
     - research               - hours
                              - rate
     + pay()      + pay()     + pay()
```

### Design decision
Use public inheritance because each derived class is a kind of Staff and should be usable through a `Staff*` or `Staff&`. Common information is private in the base class. A virtual destructor ensures correct cleanup through a base pointer.

The implementation is in `Task01/main.cpp`.

### Sample output
```text
Anita (101): Rs 79000
Bala (102): Rs 42600
Kiran (103): Rs 28000
```

## 1.3 Design defence (under 100 words)

The hierarchy stores common information and common behaviour once in the Staff base class. Each derived class overrides pay() to calculate its own salary. The program can store all staff types through Staff pointers and call pay() in one loop. To add a new category, a programmer creates another derived class and implements pay(), without changing the existing classes or the payroll loop. This reduces duplicated code and makes the program easier to extend and maintain.

## Alternative: one Staff class and a type switch

A single class could contain a type field and all possible fields (research amount, hours and hourly rate). Its `pay()` function would use `switch(type)` to select a formula. Each call still takes O(1) time. However, every object reserves space for fields that may not apply to it. Adding a category requires changing the type definition, the switch and possibly validation/creation code. With polymorphism, a new derived class can be added without editing the existing pay implementations or processing loop.

# Task 2 – From Requirement to Hierarchy

## 2.1 Identify relationships

- `Student` is a `Person`: single inheritance.
- `Staff` is a `Person`: single inheritance.
- `TeachingAssistant` is both a `Student` and a `Staff`: multiple inheritance.
- `ResearchScholar` is a `Student`: multilevel inheritance through Person → Student → ResearchScholar.
- Person is the common parent of Student and Staff: hierarchical inheritance.
- The complete design combines these forms, so it is a hybrid inheritance structure.
- An Address or Contact object stored as a member would be a has-a (composition) relationship, not inheritance.

## 2.2 Diamond problem

Without virtual inheritance, TeachingAssistant receives one Person subobject through Student and another Person subobject through Staff. This duplicates the common data and can make `name` ambiguous.

Declare both paths as virtual public bases:

```cpp
class Student : virtual public Person { /* ... */ };
class Staff   : virtual public Person { /* ... */ };
class TeachingAssistant : public Student, public Staff { /* ... */ };
```

Now TeachingAssistant contains one shared Person subobject. The most-derived class, TeachingAssistant, is responsible for constructing that virtual base.

## 2.3 Class declarations

The complete working example is `Task02/main.cpp`. It uses:
- `Person` as the common base.
- `Student` and `Staff` as virtual public derived classes.
- `TeachingAssistant` as a public derived class of both.
- `ResearchScholar` as a public derived class of Student.

Public inheritance preserves the is-a relationship and allows public base interfaces to be used through derived objects. Person's data is protected in this student example so derived classes can use it; in a larger application it could be private with protected/public accessors.

## 2.4 Access table

Visibility of a Person member inside Student:

| Person member originally | Public inheritance | Protected inheritance | Private inheritance |
|---|---|---|---|
| public | public | protected | private |
| protected | protected | protected | private |
| private | Not directly accessible | Not directly accessible | Not directly accessible |

Private base members still exist inside the base subobject, but Student cannot access them directly.

## Predict the output

Given both virtual base declarations, the output is:

```text
Person Student Staff TA
```

Person is printed once because virtual inheritance creates one shared Person base subobject. Construction order is virtual base first, then direct bases in declaration order (Student, Staff), then TeachingAssistant.

If `virtual` is removed, there are two Person subobjects. The output becomes:

```text
Person Student Person Staff TA
```

There is no required compiler error just from constructing the object in the shown code because it does not access an ambiguous Person member. An expression such as `ta.name` would be ambiguous if `name` were accessible through both paths.

## Alternative: composition

TeachingAssistant could contain a Student member and a Staff member. It would then have-a Student and has-a Staff, not be-a Student and Staff. The two contained objects would each contain their own Person subobject unless the design shares Person separately. This can increase object size because there may be two Person subobjects. Reaching a name requires selecting the member path, such as `ta.student.name`, avoiding inherited-name ambiguity. Composition is appropriate if the conceptual relationship is ownership/containment rather than is-a.

# Task 3 – Constructors in Derived Classes and Member Classes

## 3.1 Passing values to base constructors

A derived constructor calls its base constructor in its member initializer list:

```cpp
Student(...) : Person(...), course(...) { }
Staff(...)   : Person(...) { }
```

When Person is a virtual base, the most-derived class must initialize it directly. If a TeachingAssistant is created, its `Person(...)` initializer is used. The Person initializers written in Student and Staff are ignored for that virtual base during TeachingAssistant construction.

## 3.2 Member classes

`Person` contains an `Address home` member, and `Student` contains a `Course course` member. Their constructors are called in the containing class's initializer list:

```cpp
Person(...) : name(n), age(a), home(city, pin) {}
Student(...) : Person(...), regNo(reg), course(courseName) {}
```

A member object is constructed before the body of its containing class constructor.

## 3.3 Construction and destruction rules

Construction order:
1. Virtual base classes.
2. Direct base classes in the order written in the inheritance list.
3. Data members in the order declared in the class.
4. The derived class constructor body.

Destruction is the reverse:
1. Derived class destructor body.
2. Members in reverse declaration order.
3. Direct bases in reverse construction order.
4. Virtual bases last.

### Task 3 program trace
`Task03/main.cpp` demonstrates Student, Staff and TeachingAssistant construction/destruction. Address is a Person member; Course is a Student member. Student and Staff virtually inherit Person, so TeachingAssistant has one shared Person base.

## Predict the output

For the supplied Engine/Vehicle/Car program:

```text

```

Vehicle is the base class, so it is constructed first. Engine is a member of Car and is constructed next. The Car constructor body runs last. At the end of the block, destruction is reversed: Car destructor, Engine destructor, then Vehicle destructor.

### Initializer order warning
C++ initializes members in declaration order, not the order in the initializer list. If the list is written in a different order, `-Wall` may issue `-Wreorder`. The correct solution is to list initializers in the same order as the member declarations.

## Alternative: pointer to Address

With `Address* home`, the constructor must allocate an Address using `new`. The class must define ownership carefully:
- Constructor allocates the Address.
- Copy constructor performs a deep copy or uses shared ownership.
- Copy assignment safely replaces the owned Address.
- Destructor calls `delete home` if the class owns it.

A pointer adds pointer storage and dynamic allocation overhead. Access requires `home->str()`. A value member is simpler, avoids a separate heap allocation and automatically follows the containing object's lifetime. Both approaches have O(1) access to the address object; dynamic allocation adds allocation/deallocation cost.

# Task 4 – Pointers to Derived Classes: Forensics

## 4.1 Locate the defects

1. `rate()` is not virtual in the original Account class. Calls through `Account*` are bound using the static type, so the base implementation returns 3.5 even for a SeniorAccount.
2. The base destructor is not virtual. Deleting a SeniorAccount through an Account pointer has undefined behaviour. The derived destructor may not run, so its dynamically allocated `history` array is not safely released.
3. `Account copy = SeniorAccount();` copies only the Account base part. This is object slicing: SeniorAccount-specific data and behaviour are not part of the resulting Account object.
4. Storing derived objects by value in `vector<Account>` also slices them. Store smart pointers to the base class for polymorphic objects.

## 4.2 Construct evidence

The corrected program in `Task04/main.cpp` uses:
- `virtual rate()` and `override`.
- A virtual base destructor.
- `std::unique_ptr<Account>` in a vector.
- A derived destructor that releases the history array.

Compile with AddressSanitizer where available:

```bash
g++ -std=c++17 -Wall -Wextra -fsanitize=address -fno-omit-frame-pointer main.cpp -o main
```

The sanitizer should not report a leak for the corrected ownership design. Record the output produced by your own compiler and environment.

## 4.3 Repaired program

The full program is in `Task04/main.cpp`. It uses `std::make_unique` and automatically destroys all accounts when the vector leaves scope. The base destructor is virtual, so the correct derived destructor is called.

## 4.4 Prevention rules

1. A polymorphic base class should have a virtual destructor.
2. Mark overriding derived functions with `override` so signature mistakes are detected by the compiler.

## Predict the output

```text
3.5 4 3.5
```

- `p->rate()` calls the non-virtual Account function. The call is selected at compile time using the pointer's static type, Account*, so it prints 3.5.
- `p->vrate()` is virtual. The actual object is SeniorAccount, so dynamic dispatch calls SeniorAccount::vrate() and prints 4.
- `copy` is an Account object created by copying the Account base part of `s`. The derived part is sliced away. Its virtual call therefore uses Account::vrate() and prints 3.5.

## Alternative: vector of unique_ptr

Use `std::vector<std::unique_ptr<Account>>` and add derived objects with `std::make_unique<SeniorAccount>()`. Processing n accounts takes O(n) time; each call to charge/rate is O(1). Ownership is automatic and there is no manual delete loop. Smart pointers prevent common leaks and double deletion, but they do not by themselves fix non-virtual function dispatch or object slicing if objects are still copied by value.

# Task 5 – Pointers to Objects and the this Pointer

## 5.1 Four ways to reach a Cart

1. Direct object: `cart.total()`.
2. Pointer: `Cart* p = &cart; p->total()`.
3. Reference: `Cart& ref = cart; ref.total()`.
4. Dynamic object: `Cart* p = new Cart; p->total(); delete p;`.

The example in `Task05/main.cpp` demonstrates all four.

## The this pointer

`this` is an implicit pointer available in a non-static member function. It points to the current object. `*this` means the current object itself.

```cpp
Cart& setDiscount(double discount) {
    this->discount = discount;
    return *this;
}
```

`this->discount` refers to the data member, while `discount` refers to the parameter. Returning `*this` by reference supports method chaining without making a copy.

## 5.2 Array of pointers

The program creates an array of `Cart*`, checks each cart's total, and keeps a pointer to the cart with the highest total. The search takes O(n) time and O(1) extra space.

## 5.3 Comparison

| Method | Safety | Lifetime | Typical use |
|---|---|---|---|
| Direct object | Safe when in scope | Automatic | Normal local objects |
| Pointer to object | Can be null; avoid dangling pointers | Does not own target unless allocated | Optional access or polymorphism |
| Reference | Must refer to an object; cannot normally be reseated | Same as referenced object | Function parameters and aliases |
| `new` and `delete` | Manual ownership can leak or double-delete | Until delete | Dynamic lifetime; prefer smart pointers |

If `add()` returned `Cart` instead of `Cart&`, each chained call would work on a returned copy. The original object would not necessarily receive all the changes, and extra copying would occur. Returning `Cart&` modifies and returns the same object.

## Alternative: vector<Cart> instead of pointer array

A `std::vector<Cart>` stores Cart objects directly. Finding the highest total remains O(n) time. The vector stores the objects themselves rather than one pointer per object; this can use more inline storage but avoids separate object allocations. When a vector grows and reallocates, pointers/references/iterators to its elements may become invalid. An array of pointers keeps the pointed-to Cart objects at their own addresses, although the pointer array itself can still be relocated.

# Task 6 – Design Challenge: Vehicle Rental Fleet

## Stage 1 – Interpret the problem

### Entities and data
- Vehicle: registration number, daily rate, rental status.
- Bicycle: common vehicle details.
- TwoWheeler: fuel level and service due date.
- Car: seating capacity, fuel level and service due date.
- ElectricCar: seating capacity and battery capacity in kWh.
- ElectricBus: added extension example with seating and battery capacity.

### Behaviour
- Rent a vehicle if it is available.
- Return a rented vehicle.
- Calculate the charge differently for each vehicle type.
- List all vehicles.
- Add a new type without editing existing vehicle classes.

### Testable requirements
1. A vehicle can be rented only when available.
2. A vehicle can be returned only when rented.
3. Each derived type returns its own rental charge.
4. Late return adds the defined late fee.
5. The fleet can store different derived types through base-class pointers.
6. Adding ElectricBus does not require changing the existing derived classes or the listing loop.

## Stage 2 – Class hierarchy

```text
                 <<abstract>>
                    Vehicle
        ------------------------------
        - registration : string
        - dailyRate : double
        - rented : bool
        ------------------------------
        + rent() : bool
        + returnVehicle(daysLate) : double
        + rentalCharge() : double {pure virtual}
        + type() : string {pure virtual}
        + print() : void
                    ^
        ____________|____________________________
       |            |           |                |
    Bicycle     TwoWheeler     Car          ElectricCar

                         ElectricBus (new extension)
```

All vehicle classes publicly inherit Vehicle because each is a kind of Vehicle. Vehicle is abstract because it has pure virtual functions.

## Stage 3 – Critical decisions

- Common registration, daily rate and rented status belong in Vehicle.
- `rentalCharge()` and `type()` are virtual.
- The fleet is stored as `std::vector<std::unique_ptr<Vehicle>>`, which owns objects safely and supports runtime polymorphism.
- Each derived class stores only its special fields.
- Vehicle has a virtual destructor.

## Stage 4 – Class declarations and pseudocode

The complete implementation is in `Task06/main.cpp`.

### Renting pseudocode

```text
ALGORITHM RentVehicle(vehicle)
    IF vehicle is already rented
        DISPLAY "Not available"
        RETURN false
    END IF
    SET rented status to true
    DISPLAY "Rental successful"
    RETURN true
END ALGORITHM
```

### Returning pseudocode

```text
ALGORITHM ReturnVehicle(vehicle, daysLate)
    IF vehicle is not rented
        DISPLAY "Vehicle was not rented"
        RETURN 0
    END IF
    SET rented status to false
    SET charge = vehicle-specific rentalCharge()
    IF daysLate > 0
        ADD daysLate * lateFeePerDay to charge
    END IF
    RETURN charge
END ALGORITHM
```

### Charge policy used in this example

The assignment does not provide exact rates or a late-fee amount, so the program uses clear demonstration values:
- Late fee: Rs 200 per late day.
- Bicycle charge: daily rate.
- Two-wheeler: daily rate + fuel litres × Rs 5.
- Car: daily rate + fuel litres × Rs 5 + seats × Rs 10.
- Electric car: daily rate + battery kWh × Rs 3 + seats × Rs 10.
- Electric bus: daily rate + battery kWh × Rs 3 + seats × Rs 5.

These are example rules for demonstrating polymorphism, not values specified by the assignment.

## Stage 5 – Implementation and demonstration

The program:
- Creates a bicycle, two-wheeler, car and electric car.
- Adds an ElectricBus without changing existing vehicle classes.
- Lists the fleet.
- Rents each available vehicle.
- Returns the car two days late and adds the late fee.
- Returns the electric bus on time.
- Lists the fleet again to show the updated rental status.

## Alternative: one Vehicle class with a type code and switch

A single Vehicle class could hold every possible field and use `switch(type)` inside `charge()`. A switch and a virtual call are both O(1) per charge calculation. The single class reserves space for fields that many vehicle types do not use. A polymorphic object generally has a vtable pointer overhead, while each derived class stores only relevant fields. Adding a new type to the switch design requires editing the Vehicle class and switch logic. With the hierarchy, a new derived class can be added by implementing the required virtual functions without changing the existing classes.
